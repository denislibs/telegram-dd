## Вердикт: SOUND WITH FIXES (C1 и C2 блокируют T2)

Каркас верный, и я бы его сохранил: action/reducer/selector-слой tt остаётся иммутабельным, на границе стоит один
проход (walk) по структурному разделению, тот же проход пишет журнал в формате `deepDiff`, а `withGlobal` вызывается
в теле компонента. Журнал корректнее, чем показывают тесты ветки: моя более жёсткая property-проба (3000 раундов,
вложенные формы, смена типа и `id`, несколько журналов подряд, отложенная отправка) проходит. Стоимость прохода
не больше стоимости спредов tt, которые его порождают, в том числе на широких словарях.

Не держится главное обещание, ради которого выбран этот вариант: «слой действий tt портируется байт-в-байт без
изменения семантики». Код tt опирается на **семантику значений**: объект, полученный из global, никогда не меняется.
Правило прохода «сливать объект на месте, если у него тот же `id` или `id` нет вовсе» эту гарантию нарушает. Пробы
находят тихие поломки в неизменённом коде tt: самый частый апдейтер (`updateChat`), откаты оптимистичных
обновлений, порча списков, кэши по идентичности, смена темы, роль master-вкладки (C1, C2). Исправление локальное:
правило слияния в `apply.ts` плюс короткий список отклонений в `src/global`. Прототип исправления (вариант A ниже)
проходит те же пробы и бенч с теми же цифрами. Править это нужно до массового импорта actions (T2): каждый
скопированный файл добавляет мест, где придётся искать такие ошибки.

## Critical

### C1. Слияние на месте ломает семантику значений tt: захваченные объекты, откаты, алиасы, кэши, константы

**Где:** `src/global/store/apply.ts:202` (`isLiteralObject(nv) && isLiteralObject(pv) && sameEntity(pv, nv)` →
`applyObject` сливает `nv` в `pv` на месте); обоснование в `docs/store-architecture.md:48-57`, `:65-71`.

**Суть.** После `setGlobal` любой объект, который код tt получил из global _до_ записи, уже несёт новые значения:
`pv` это тот самый сырой объект, на который ссылается захваченная переменная. В tt такая переменная оставалась
снимком. Сущность с `id` не защищает правило «другой `id` → замена»: `id` совпадает, и объект сливается. Объекты без
`id` (записи tab state, `boostStatus`, `searchParams`, `ApiSavedStarGift`, `content`, `threadInfo`) сливаются
**всегда**, даже если `nv` это другой объект, живущий в дереве по другому пути.

**Сценарии (все подтверждены пробами, код tt не изменён):**

1. **`actions/apiUpdaters/chats.ts:54-125`, `updateChat`, самый горячий апдейтер чатов.** В нём
   `const localChat = selectChat(global, id)` → `setGlobal(updateChat(...))` (стр. 81) → затем
   `changedFields = keys.filter(k => localChat[k] !== chatUpdate[k])` (стр. 112). Список всегда пустой, поэтому
   `invalidateFullInfo` для `INVALIDATE_FULL_CHAT_FIELDS` не вызывается никогда. Сравнение
   `localChat.linkedCommunityId !== chatUpdate.linkedCommunityId` (стр. 118) всегда `false`, `loadFullCommunity` не
   вызывается.
2. **Откат к захваченному объекту превращается в no-op.** `actions/api/payments.ts:870-946` `applyBoost`: в
   `oldStatus = tabState.boostModal.boostStatus` при оптимистичной записи сливается новое значение, и
   `boostStatus: oldStatus` в ветке «Rollback local changes» уже ничего не меняет. В
   `actions/api/stars.ts:454-478` `changeGiftVisibility` то же самое: контейнер `oldGifts` (без `id`) получил новое
   свойство `gifts`, и откат на `oldGifts.gifts` пишет новые подарки.
3. **Алиас элемента списка в слоте портит список.** `actions/ui/stars.ts:366-389` `selectGiftForCraft`: в `gift1`
   кладётся элемент `giftCraftModal.myCraftableGifts` (прокси из props компонента, проход его разворачивает в сырой
   элемент). Повторный выбор другого подарка в тот же слот вливает подарок B _в объект подарка A_, который всё ещё
   лежит в списке. Список становится `['b', 'b']`. Обмен двух объектов без `id` между ключами
   (`{ s1: s2, s2: s1 }`) теряет один из них: `['B', 'B']`.
4. **Одинаковый `id` не означает ту же сущность.** Id сообщений уникальны только внутри чата, а id приватного чата
   совпадает с id пользователя. Слот `oneTimeMediaModal.message` (`types/tabState.ts:989`) с сообщением 5 из чата B
   поверх сообщения 5 из чата A переписывает `messages.byChatId.A.byId[5]` содержимым из B.
5. **Кэши по идентичности отдают устаревшие данные.** `selectors/audioPlayer.ts:128-150` (`SEGMENT_BY_SEARCH_PARAMS`,
   `INDEX_BY_KEYS`: при подгрузке сегментов `searchParams` сливается на месте, ключ WeakMap прежний, отдаётся старый
   сегмент, и в плейлисте ломаются next/prev), `helpers/messageMedia.ts:173`
   (`AUDIOS_BY_RICH_MESSAGE`). План (`plans/2026-10-14-store.md:13`) называет этот кэш «fine: the object identity is
   stable now», а на деле стабильная идентичность при изменившемся содержимом и делает кэш устаревшим. Сюда же
   `util/memoized` (`selectors/wallet.ts`, `selectors/ui.ts`) и `useMemo(…, [chat])` в компонентах.
6. **Константы модулей попадают в дерево и мутируются.** `reducers/passcode.ts:26-38` `clearGlobalForLockScreen`
   раскрывает `...INITIAL_GLOBAL_STATE` и `{ ...INITIAL_TAB_STATE, … }` без `cloneDeep`. Вложенные объекты констант
   записываются по ссылке, и следующее слияние пишет в саму константу. Проба: `constant.globalSearch.query`
   становится `'secret'`, и это значение получит следующая новая вкладка.

Эвристический поиск по `src/global/actions` в tt (`const x = select…(global)` → `setGlobal` → чтение `x.field`)
находит **61 кандидата** (`api/chats.ts`, `api/bots.ts`, `api/stars.ts`, `apiUpdaters/messages.ts`, …). Значимы не
все, но выловить их вручную, а потом повторять это на каждой синхронизации с upstream, нереально.

**Исправление: вариант A, «заменять по умолчанию, сливать только контейнеры».** Прототип проверен:

- Проход сливает на месте только **структурные контейнеры**: корень, срезы верхнего уровня, словари (`*ById`,
  `byChatId`, `byTabId`, `byKey`, `listIds`, `lastMessageIds`, …) и записи-контейнеры непосредственно под ними
  (`messages.byChatId.*`, `*.threadsById.*`, `byTabId.*`). Список явный, путевые шаблоны лежат в одном файле
  `store/containers.ts` (около 30 строк). Тест сверяет его с `GlobalState`.
- Любой другой изменившийся объект (сущность или запись-значение) **заменяется** свежим объектом из `next`, если
  они не shallow-equal. Если же `nv` уже живёт в дереве, он записывается по ссылке, как алиас в tt. Сущности и
  записи становятся неизменяемыми значениями, и семантика tt возвращается во всех шести сценариях. Проба на
  прототипе: `localChat.title` остаётся `'A'`, откат работает, список крафта остаётся `['a', 'b']`, обмен даёт
  `['B', 'A']`. Проверку shallow-equal добавить обязательно: без неё `replaceUsers` (5k свежих копий) делает 5000
  записей за 4,3 мс, с ней 100 записей.
- Контейнер, который записывается целиком (новый ключ), копируется поверхностно. Иначе контейнер, взятый из
  константы, начнёт мутироваться (п. 6).
- Цена: зернистость обновления сущности становится «на строку», как в tt: на мэппер строки плюс привязки
  `props.chat.*`, вместо «на поле». Бенч на прототипе (production, M1 Pro): новое сообщение 253 мкс / 2 пересчёта
  (было 237 мкс / 2), reorder 26 мкс, `updateTabState` 2,4 мкс, `updateUsers` 100/5k 624 мкс (было 647). Разницы
  практически нет.
- Новая зависимость: при замене записи, которая переиспользует большое поддерево, ни разу не прочитанное через
  прокси, `adopt()` в движке обходит его заново. Измерено 1,7 мс на запись для 5k элементов результатов поиска, см.
  I6 и движковый пункт E3′.

Альтернатива B (оставить слияние сущностей «по полям»): сливать только сущность с тем же `id` в её **каноническом**
словаре и только когда `nv` не является объектом дерева (нужна пометка «принадлежит store» в движке). Плюс
аудит 61 места и отклонения вида `const localChat = { ...selectChat(…) }`. Тогда весь этот класс тихих ошибок
приходит заново с каждым upstream sync. Брать B стоит только как точечный opt-in для словаря, на котором профиль
покажет, что замена дорога.

Документ нужно поправить. В §1.2 обоснование правила `id` ссылается на `chat.lastMessage`, который «часто тот же
объект, что `messages.byId[id]`», но в tt `090e38f` у `ApiChat` нет `lastMessage`: последнее сообщение хранится как
id в `chats.lastMessageIds`. Бенч моделирует ту же несуществующую схему (I4).

### C2. Колбэки получают живой корень, и все потребители `prevGlobal` / «последнего снимка» молча перестают срабатывать

**Где:** `src/global/index.ts:120` (`cb(rawGlobal, diff, remoteDiff)`); план, `plans/2026-10-14-store.md:57`: строка
«unchanged where they compare primitives (values still differ)» **неверна**.

**Суть.** `prevGlobal = global` сохраняет _тот же_ корневой объект. При следующем вызове `prevGlobal.x.y` читается
живьём и равно текущему значению, причём для примитивов тоже. Подтверждено пробой: колбэк в стиле
`ui/settings.ts`, который сравнивает `sharedState.settings.theme`, после смены темы видит `[]`, а в tt видел
`['dark']`.

**Затронуто (код tt без изменений):**

- `global/actions/ui/settings.ts:26-80`: `switchTheme`, `oldSetLanguage`, `applyPerformanceSettings`,
  `updatePeerColors` **не вызываются никогда**. Смена темы и языка в настройках не применяется.
- `global/intervals.ts:17-31`: `isPreviousMaster === isCurrentMaster` всегда, если не считать первого вызова.
  Вкладка, потерявшая роль master, не останавливает интервалы. Вкладка, повышенная до master, их не запускает:
  истечение stories, shortpoll каналов, эфемерные таймеры не работают.
- `global/shared/sharedStateConnector.ts:33-80`: после первой локальной правки `lastSharedState = update` становится
  живым объектом дерева. Дальше `global.sharedState === lastSharedState` и `deepDiff(lastSharedState, …)` дают
  «нет изменений», и локальные изменения shared state больше не уходят в SharedWorker (другие вкладки и аккаунты).
- `util/emoji/customEmojiManager.ts:11-26` и `util/folderManager.ts` (в плане они уже есть).

**Исправление.** В T4 переписать **все** потребители `prevGlobal` / `lastX` (6 файлов) на `diff`/`remoteDiff` или на
собственные снимки примитивов (`let prevTheme = …`). Если нужен снимок объекта, делать явный `structuredClone`.
Исправить таблицу T4 и §12 («zero non-import lines under src/global» на явный список отклонений). Добавить
lint-правило, запрещающее сохранять `global` в переменную модуля внутри `addCallback` (по аналогии с
eslint-правилами `tt-multitab/*` в tt).

## Important

### I1. Multitab: отложенный локальный журнал перетирает более новое значение, пришедшее от master (tt сравнивает итоговые состояния)

**Где:** `src/global/store/apply.ts:60-72` (`journalSet` хранит значение примитива на момент записи),
`src/util/browser/multitab.ts:197` (diff строится в колбэке, а отправляется на `onFullyIdle`, до 500 мс).
Подтверждено пробой: slave локально пишет `unread = 0`, затем получает от master `unread = 7` (`fromRemote`),
затем отправляет свой diff. Итог: master `0`, slave `7`, вкладки разошлись. В tt flush считает
`deepDiff(lastBroadcastDiffGlobal, currentGlobal)` по _итоговому_ состоянию и отправил бы `7` или ничего, поэтому
§5 плана («same class as tt's») не прав. **Исправление:** записи журнала для примитивов разрешать при конвертации
(хранить `parent` и `key`, читать `parent[key]`), а саму конвертацию перенести в `flushBroadcastDiff`. Тогда
удалённые записи, пришедшие в промежутке, попадут в diff, и такой эхо-ответ безвреден: значение совпадает с
master. Округление: сейчас diff содержит живые ссылки на объекты дерева до момента `postMessage`. Это безопасно,
моя проба с отложенной отправкой проходит, но стоит отметить в комментарии.

### I2. Код tt мутирует сырое дерево; DEV и prod ведут себя по-разному

**Где:** `src/global/index.ts:147-154` (DEV: поверхностная копия, prod: сам корень), `apply.ts:139-150`
(`keyCounts`). Места в tt: `actions/api/stories.ts:67,73,110,116` (`global.stories.stateHash = …`, мутация
**вложенного** объекта дерева) и `global/init.ts:127` (`global.isCacheApiSupported = …` по корню).

- DEV, вложенная мутация: если объект уже посещался, следующий проход бросает «written outside setGlobal». Ошибка
  плавающая: зависит от того, посещался ли `stories` раньше. Подтверждено пробой.
- prod: изменённый лист не уведомляет подписчиков (проба: memo остаётся со старым значением). Если появился новый
  ключ, закэшированный счётчик ключей занижен, и более позднее удаление в этом объекте **пропускается**
  (проба: `hasNext` остаётся в дереве). Мутация корня в prod даёт тот же эффект на корне, в DEV её «поглощает»
  копия.
- **Исправление:** в prod тоже возвращать поверхностную копию (0,2 мкс, поведение DEV и prod совпадёт); 4 строки
  в `stories.ts` поправить как `// Deviation:`; lint по шаблону `\bglobal(\.\w+){2,}\s*=`; в DEV-ошибку
  `keyCountOf` добавить путь (документ на `:377` обещает путь, а его нет; к тому же проверка ловит только
  изменение числа ключей, а не изменение значения).

### I3. `withGlobal` расходится с контейнером tt по устойчивости и приоритету props

**Где:** `src/global/index.ts:267-289`. (a) Исключение в мэппере не перехватывается. tt оборачивает
`mapStateToProps` в `try/catch` → `handleError` и сохраняет прежние props (`teactn.tsx:204-210, 303-307`), а мэпперы
tt действительно бросают на переходных состояниях. Нужно `try { … } catch (e) { handleError(e); return last; }`.
(b) `activationFn` игнорируется на первом запуске (`if (activationFn && last && …)`): tt не вызывает мэппер у
неактивного контейнера. (c) `mergeProps(() => mapped(), ownProps)` пропускает к значению из мэппера собственный
prop, переданный как `undefined`, а в tt `{...mapped, ...own}` побеждает own даже со значением `undefined`.
Достаточно задокументировать или сделать проверку на присутствие ключа. Замечание без претензии: подписка
«на поле» на самом деле работает «на запись мэппера». Любая смена ключа записи заново выполняет все привязки,
читающие state-props (`getFrom` читает `mapped()`). Это зернистость tt, но формулировку «per-field granularity» в
§5.1 стоит смягчить.

### I4. Бенч и цифры в §4 расходятся с тем, что реально измеряется

- «edit one message … ≤3 writes, 1 row» (`store-architecture.md:142`): прогон даёт **0,0 пересчётов и 0,3 записи**.
  Индекс постоянный (`scripts/bench/store.ts:451`), он попадает в сообщение, добавленное после подписки, а текст
  `edited ${Date.now()}` в пределах одной миллисекунды повторяется, поэтому сценарий почти всегда no-op. Нужен
  счётчик в тексте и подписанное сообщение.
- Схема бенча хранит `chat.lastMessage` (`store.ts:46`), а в tt `090e38f` этого поля нет: путь нового сообщения в tt
  пишет `chats.lastMessageIds.all` (ещё один словарь на 2k ключей).
- «60k objects» (`:149`, `:162`, `:324`): в бенч-состоянии около **330k** объектов (по 6 на сообщение). При этом tt
  кэширует не больше 200 чатов и 500 пользователей (`config.ts:52-53`), так что реальный холодный старт из кэша
  примерно на порядок меньше 49 мс. Тяжёлый случай другой: `globalUpdate` (полное состояние master) для новой
  вкладки, и мерить надо его. Разбивка холодного старта: 58 мс против обхода `Object.keys` за 16 мс и `isWrappable`
  за 27 мс; остальное это накладные расходы `adopt()` на объект (`WeakMap.has`, `Set.add`, чтение `$RAW`). Для
  сравнения, `structuredClone` того же дерева 111 мс, `JSON.parse` 40 мс.
- Стоимость контейнеров tt («hundreds of mapStateToProps») не измерена, а она часть сравнения.
- Широкие словари: утверждение подтверждается. Одно изменение в словаре: проход 0,12 мс против спреда tt 0,34 мс
  (2k именованных ключей); 0,89 против 2,1 мс (10k); 1,6 против 5,5 мс (50k индексных). Скрытого O(n) сверх того,
  что tt уже платит спредом, на горячих путях (вставка сообщения, reorder, статусы и typing) нет. Цифры
  воспроизводятся: новое сообщение 237 мкс, reorder 26 мкс, холодный старт 55 мс в production.

### I5. Контракт codemod (§12) не сходится с прототипом в мелочах, которые сломают компиляцию

- `withGlobal<OwnProps>(…)` с явным аргументом типа, как в tt, не скомпилируется: в прототипе
  `withGlobal<OwnProps, StateProps>` объявлен с двумя обязательными параметрами (`index.ts:267`), получится TS2558.
  Правило: удалять аргументы типа или дать `StateProps` значение по умолчанию.
- Деструктуризация со значениями по умолчанию (`({ isOpen = false })`) при переписывании в `props.isOpen` теряет

### Новые находки

#### N1 (Important). Прокси контейнера, переданный из компонента в action, кладёт в committed global копию, принадлежащую store, и следующий walk её мутирует

**Где:** `src/global/store/apply.ts` (`const raw = unwrap(nv); if (raw !== nv) next[key] = nv = raw` в
`applyContainer` и аналогичная строка в `copyContainer`; в движке `adopt()` делает то же самое с прокси, вложенными
в сущности и массивы). У сущности `unwrap` возвращает сырой объект tt, и всё в порядке. У **контейнера** он
возвращает приватную копию store. Эта копия попадает в committed global второго пути, а walk по первому пути
продолжает сливать в неё изменения.

**Проба** (подтверждена): `gift1` (запись без `id`, то есть копия store) → компонент вызывает action с
`gift2: props.gift1` → затем `gift1` выбирается заново. Итог: committed `gift2.slug === 'b'` (тот же объект, снимок
был `'a'`), в зеркале `gift2 === 'a'`. Committed global изменился без `setGlobal`, committed и зеркало разошлись в
противоположные стороны, а `deepDiff` для multitab и кэш этого изменения не видят. По сути это C1, пришедший через
другую дверь. Реальный путь в tt: `GiftInfoModal` (`modal.gift`, `ApiSavedStarGift` без `id`) →
`openGiftUpgradeModal({ gift: savedGift })` / `openGiftResalePriceComposerModal({ gift })`. Под тот же класс попадают
`ApiFormattedText` черновика, переданный в action, и `{ ...props.someRecord }`: спред прокси несёт прокси вложенных
контейнеров.

**Исправление:** вести `WeakSet` копий, которые создаёт `copyContainer`. Если `unwrap(nv)` возвращает объект из
этого набора, в `next[key]` писать **свежую копию** (`copyContainer(raw)` подходит: контейнеры копируются, сущности
и массивы остаются общими). Для прокси, вложенных в сущность или массив, нужна DEV-проверка на один уровень или
запись в документе. Исправить в §1.2 строку «a store proxy … the committed global gets the raw object»: для
контейнеров это неверно. Добавить регрессионный тест по пробе выше.

#### N2 (Important). Кэши по идентичности, ключом которых служит контейнер, в мэпперах устаревают и теряют подписку

Контейнеры зеркала имеют стабильную идентичность: копия сливается на месте. Кэш в коде tt, ключом которого служит
контейнер, в контексте компонента всегда попадает в старую запись. При попадании в кэш мэппер ничего не читает и
поэтому теряет зависимости. Подтверждено пробами: `memoized((bots, users) => …)` в форме `findWalletBotId` даёт
`[undefined, undefined]`, хотя committed global уже даёт `'w'`; WeakMap в форме `SEGMENT_BY_SEARCH_PARAMS` даёт
`'old'`, хотя должно быть `'new'`. Места в tt: `selectors/wallet.ts` (`selectWalletBotId` в мэппере
`LeftSideMenuItems`, `selectReplacedWalletBotId` в `useSelector` у `AttachMenu`, `selectAvailableCurrencies` по
`currencyRates` у `WalletCurrencyScreen`), `selectors/ui.ts` (`selectActionMessageBg` →
`memoized(theme, settings.themes[theme])`: фон action-сообщений не обновится после смены обоев),
`selectors/audioPlayer.ts` (`selectPlaylistKeys` в `AudioPlaylistModal`). Кэши, ключом которых служит сущность или
массив, работают: при изменении это новый объект. Утверждения §1 («identity caches … see tt's objects») и T4
плана верны только для контекста actions.

**Исправление:** отклонение на одну строку в `util/memoized` и в 2 WeakMap из `audioPlayer.ts`: если один из
аргументов это прокси store (`unwrap(a) !== a`), кэш обходится (мэппер и так работает в memo). Тест по пробе. В
контракт codemod (§12.7) добавить пункт: props-контейнеры не меняют идентичность, поэтому deps `useEffect`/`useMemo`,
где указан контейнер, нельзя переводить в отслеживание идентичности.

#### N3 (Important). `getGlobal()` внутри helpers, вызванных из мэпперов, ничего не отслеживает: UI устаревает

В tt каждый мэппер перезапускался на каждый `setGlobal`, поэтому чтение `getGlobal()` внутри helper было
безопасным. Здесь мэппер перезапускается только по отслеживаемым чтениям. Проба: memo с
`getGlobal().chats.byId.a.title` после записи `'A3'` отдаёт `'A2'` и больше не запускается. Места: verbatim-helpers
`helpers/chats.ts:170` (`getCanPostInChat` → `selectIsChatRestricted`, мэппер `MiddleColumn:794`,
`RecipientPicker`), `helpers/chats.ts:402` (`getPeerColorCount` → `global.peerColors`, `usePeerColor`),
`helpers/messages.ts:83` (`getMessageTranscription` через `messageSummary`: превью в списке чатов не покажет
пришедшую транскрипцию), `helpers/peers.ts:34`, `helpers/misc.ts:53`, `renderMessageSummaryHtml.ts:14`. Codemod их
не увидит: вызов транзитивный и сидит в коде, импортированном verbatim. E2 даёт только DEV-предупреждение. Пробел
не связан именно с зеркалом (он был и в прототипе 0), но в исходном ревью я его пропустил.

**Исправление** (без переключения семантики): `getGlobal()` читает сигнал версии, который `setGlobal` увеличивает
на каждую запись. Вне отслеживания это no-op, внутри мэппера получается ровно поведение контейнера tt («перезапуск
на каждую запись»), и только для тех мэпперов, которые действительно трогают `getGlobal()`. Плюс DEV-счётчик таких
мэпперов, чтобы со временем перевести их на явный `global`. Альтернатива: 7 отклонений в helpers.

#### N4 (Important, остаток I5). `withGlobal<OwnProps>(…)` типизирует state-props как `any`

TypeScript не умеет частичный вывод: с одним явным аргументом второй берёт значение по умолчанию `AnyLiteral`.
Проба через tsc: `props.doesNotExist` компилируется (`@ts-expect-error` не используется), `props.isLeft` имеет тип
`any`. Без аргумента типа вывод работает полностью (проба зелёная, опечатка ловится). §5.1 и правило §12.2 («the
type argument may stay») молча выключают проверку типов во всём слое компонентов. **Исправление:** codemod удаляет
аргумент типа, значение по умолчанию заменить на `{}` (тогда забытый `<OwnProps>` падает громко на первом же
`props.stateProp`). Замечание: `props.b ?? 1` отличается от значения по умолчанию в деструктуризации на `null`.

#### N5 (Important). DEV-скан из N1 делает каждую запись в DEBUG в 58 раз медленнее

**Где:** `src/global/store/apply.ts`, `sanitize()`: `if (devChecks) devScan(raw, path, 0)` выполняется для **любого**
изменённого значения, включая контейнеры. При новом сообщении walk вызывает `sanitize` на корне для `messages`,
`chats`, `byTabId` и на каждом следующем уровне снова, а `devScan` каждый раз проходит 4 уровня. Для `messages` это
`byChatId → чат → byId → сообщение`, то есть все сообщения. `setDevChecks(DEBUG)` включён везде, где
`APP_ENV !== 'production'`: dev-сервер и `playwright.config.ts` / `playwright.visual.config.ts`
(`vite --mode development`).

**Проба** (копия бенча с `setDevChecks(true)`, production-сборка frameact, чтобы изолировать скан):

| сценарий                      | prod    | DEV-скан сейчас | DEV-скан только по значениям, записанным по ссылке |
| ----------------------------- | ------- | --------------- | -------------------------------------------------- |
| новое сообщение               | 0,65 мс | **37,5 мс**     | 0,66 мс                                            |
| edit сообщения                | 0,33 мс | **34,3 мс**     | 0,35 мс                                            |

Каждая находка к тому же выдаётся 3–4 раза: один и тот же объект сканируется с каждого уровня.

**Исправление** (проверено пробой): сканировать только значения, которые пишутся по ссылке, то есть массивы и сущности.
Контейнеры walk и `copyContainer` и так обходят уровень за уровнем, на каждом вызывая `sanitize`, поэтому прокси в

```ts
if (devChecks && (Array.isArray(raw) || isEntity(raw, path))) devScan(raw, path, 0);
```
